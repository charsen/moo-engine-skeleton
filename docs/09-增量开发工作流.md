# 第 9 章　日常增量开发：改表与加接口

目标：为现有 `foods` 表增加库存字段、自定义状态接口和移动端只读接口，
掌握 scaffold 的增量开发流程。

---

## 9.1 先区分两类文件

`moo:free` 只负责首次生成。后续改字段、加接口时，先分清生成器如何处理文件：

> **哪些文件生成器会自动覆盖、哪些必须自己手动补？**

- **再生成区**：每次生成都会覆盖，例如枚举访问器、语言包和 ACL 派生物；不要手改。
- **只生成一次**：文件存在时会跳过，例如 `$fillable`、校验规则和控制器逻辑；后续手动维护。

判断标准很简单：能从 yaml 完整推导的内容会被覆盖；包含业务逻辑的内容通常只生成一次。
两个同名 `FoodTrait.php` 因职责不同，所属区域也不同。

**前提**：已完成第 7 章，moo-system 和 ACL 可用，后台账号为
`13800000000` / `admin888`。
开发服务器按惯例跑在 8088：

```bash
PHP_CLI_SERVER_WORKERS=4 php artisan serve --host=127.0.0.1 --port=8088 --no-reload
```

全章约定：

- **工作目录**：本章所有 `php artisan` / `./vendor/bin/pint` / curl 命令都在
  **`engine/` 目录内**执行（仓库根没有 `artisan`，Laravel 应用在 `engine/` 子目录）。
- **输出里的路径基准**：当前 moo-scaffold 会把迁移输出和 `git add` 提示都写成
  **`engine/` 相对路径**；本章命令统一在 `engine/` 目录执行，所以直接使用
  `database/migrations/...` 即可。若旧版包输出带 `engine/` 前缀，去掉前缀后仍是同一个本地文件，
  不要再额外创建一层 `engine/`。
- **最短必做主线：9.2–9.7**——加字段、补生成一次区、加 action、同步 ACL/文档、测试、真机冒烟。
- **业务扩展：9.8–9.9**——需要移动端只读接口或专属 Resource 时再做，不阻塞前面的增量闭环。
- **按需参考：9.10–9.12**——只在数据迁移、依赖升级或兼容旧前端时查阅，不要求顺序跟做。
- 第 7 章已把统一诊断助手复制到 `tools/tutorial-http.sh`；本章真机命令复用它，
  不再重复手写 HTTP 状态拆分和 token 解析。

## 9.2 加字段：yaml → moo:fresh → moo:migration

### ① 真相源先行：编辑 yaml

一切结构改动从 `scaffold/database/Food.yaml` 开始（**不要**直接写迁移）。
这份 yaml 是 `tables: → foods: → fields:` 的三层嵌套（每层缩进 4 空格，后文 9.8.1 /
9.9.1 改的 `controller:` 也在 `foods:` 下同一层）。在 `fields:` 里 `price` 之后
加一行，沿用行内 map 风格：

```yaml
tables:
    foods:
        # ……model / controller / attrs / index 各段略
        fields:
            # ……
            price: { name: 价格, type: int, default: 0, desc: '单位：分' }
            stock: { name: 库存, type: int, default: 0 }   # ← 新增这一行
```

### ② moo:fresh 重建缓存

改完任意 schema yaml 后必须跑（第 2 章讲过，所有生成器都读这份缓存）：

```bash
php artisan moo:fresh
```

```
🔍 ./scaffold/database/Food.yaml .... Parsed
🔄 ./scaffold/models.php / model_ids.php / controllers.php / tables.php
   / enums.php / foods.php / database/_fields.yaml / fields.php .... Updated
SUCCESS ✅ Completed.
```

`moo:fresh` 只重建缓存和 scaffold 派生文件，不修改 `app/` 下的代码。

### ③ moo:migration 生成增量迁移

```bash
php artisan moo:migration --help
# Usage: moo:migration [options] [<schema_name>]   （Ex: System；--table=... 可限定单表）

php artisan moo:migration Food
```

```
ℹ️  1 个 migration 文件已生成
  + database/migrations/2026_07_22_020659_update_foods_table.php

提示: scaffold 不再自动 git commit。请手动:
  git add scaffold/database/Food.yaml scaffold/database/.snapshots/Food.yaml database/migrations/...

 💬 现在就执行 'artisan migrate' 吗 (yes/no) [yes]:
 > 🎯 Running migrate
  2026_06_11_143750_update_foods_table .... 38.04ms DONE
```

三个要点：

1. **生成的是增量 `Schema::table`，不是重建表**——核心内容：

   ```php
   public function up(): void
   {
       Schema::table('foods', static function (Blueprint $table) {
           $table->integer('stock')->unsigned()->default(0)->comment('库存')->after('price');
       });
   }

   public function down(): void
   {
       Schema::table('foods', static function (Blueprint $table) {
           $table->dropColumn('stock');
       });
   }
   ```

   连 `->after('price')` 都按 yaml 里的字段顺序排好了；`int` + `default: 0` 推导成
   `unsigned()->default(0)`，注释取 yaml 的 `name`。它怎么知道「只加了 stock」？
   diff 的基准是 `scaffold/database/.snapshots/Food.yaml` 快照（数据库设计器用的同一套
   diff + writer）。**快照 + yaml + 迁移要一起提交**，否则下次 diff 基准错乱。

2. **末尾追问 `现在就执行 'artisan migrate' 吗 (yes/no) [yes]`，默认 yes**——非交互管道下
   会直接取默认值把迁移跑了，脚本里调用时要心里有数。跑完用
   `SHOW COLUMNS FROM foods` 确认：`stock int(10) unsigned NOT NULL DEFAULT 0`，
   位置正好在 price 之后。

3. **可以放心重复执行**：纯枚举标签改动（见 9.3 的 i18n 一节）后再跑一次
   `moo:migration Food`，输出 `ℹ️ 无变更,跳过生成 migration。`——它只对结构性变更
   产出迁移。

## 9.3 手补「生成一次」的文件（本章核心）

数据库有 stock 了，但代码层还不认识它。9.1 定义的两类文件——
「再生成区」（每次生成都覆盖）和「只生成一次」（已存在就跳过）——增量开发时
这条边界决定了你的手工清单。

### 9.3.1 更新再生成区

```bash
php artisan moo:model Food
```

```
💤 ./app/Models/Food/Food.php ............... Model already exists   ← 生成一次，跳过
🔄 ./app/Models/Food/Traits/FoodTrait.php ............... Updated   ← 再生成区，覆盖
🔄 ./app/Models/Food/Enums/FoodCategory.php ............. Updated
🔄 ./app/Models/Food/Enums/FoodStatus.php ............... Updated
```

确认两点：

- `Food.php`（Model 本体）**只生成一次**，已存在就 💤 跳过——`$fillable` / `$attributes`
  这些必须自己补（下一小节）。
- `Traits/FoodTrait.php`、`Enums/*.php` 是**再生成区，被无条件覆盖**。本次覆盖后与
  已提交版本的 diff 只剩代码风格差异（生成器输出 `<?php declare(strict_types = 1);`
  单行风格、`(int)$x` 不带空格；仓库里的版本被 pint 格式化过）。9.6 跑完 pint 后这些
  文件与提交版本**字节级一致**——即「再生成区被覆盖 + pint 收尾 = 无净变更」
  （stock 不是枚举字段，不会新增 `getStockTxtAttribute` 之类访问器）。
  **结论：重生成再生成区永远是安全的，后面跟一次 pint 即可。**

### 9.3.2 手补 Model（`app/Models/Food/Food.php`，3 处）

打开 `app/Models/Food/Food.php`，找到并修改以下 3 处：

**① docblock（文件顶部，class 定义之前）**
在 `@property int $price` 之后添加：
```php
/**
 * ...
 * @property int $price 价格
 * @property int $stock 库存
 * ...
 */
class Food extends Model
```

**② `$attributes` 默认值数组**
在 `'price' => 0,` 之后添加：
```php
protected $attributes = [
    'food_category' => 1,
    'price' => 0,
    'stock' => 0,  // ← 新增
    'calories' => 0,
    // ...
];
```

**③ `$fillable` 批量赋值白名单**
在数组中找到 `'price'`，在其后添加 `'stock'`：
```php
protected $fillable = [
    'food_name', 'price', 'stock', 'calories', // ...
];
```

漏改 `$fillable` 的症状最阴险：create/update 接口照样返回 201/200，但 stock 被
批量赋值**静默丢弃**，库里永远是默认值。

### 9.3.3 手补 Request（`app/Admin/Requests/Food/Food/{Store,Update}Request.php`，各 2 处）

两个文件改法相同：

```php
// rules() 里 price 之后：允许旧客户端省略字段，但显式 null 必须返回 422，不能落到数据库 500
'stock' => ['sometimes', 'required', 'integer', 'min:0'],

// formLayout() 里 price 之后：
['stock'],
```

`formLayout()` 不补的话，`/scaffold` 调试器和前端的 create/edit 表单不会出现该控件。
IndexRequest 的筛选支持本次未加（可选项；要加的话还得同步 ModelFilter）。
这里不要写 `nullable`：schema 是 `NOT NULL DEFAULT 0`，而 store / update 会把 validated 数据直接写库；
`nullable` 会让显式 `stock: null` 通过校验后触发 SQL 异常。`sometimes|required` 的语义是
“兼容旧客户端不传；一旦传了就必须是非空的非负整数”。

### 9.3.4 手补 Controller 侧硬编码字段清单（最容易漏的两处）

- `app/Admin/Controllers/Food/Traits/FoodTrait.php`——注意 **controller 的 trait 是
  「生成一次」的，和 Model 的同名 trait（再生成区）不是一类**！（为什么同名却待遇相反，
  回看 9.1 的判断标准：Model 侧能从 yaml 推导，controller 侧是要按业务裁剪的清单。）
  `getListFields()` 的 `$fields` 数组、`getListColumns()` 的 `$columns` 数组各加 `'stock'`。
  漏掉的症状：列表接口查不出 / 表头不显示新字段。
- `app/Admin/Controllers/Food/FoodController.php` 的 `show()`：第 2 章真实生成的初版只有
  `$columns`，并没有 `$fields`。把查询和列清单明确改成下面这样（不是去找一个不存在的数组）：

  ```php
  $fields = ['id', 'food_name', 'food_category', 'price', 'stock', 'calories',
      'food_status', 'description', 'deleted_at', 'created_at', 'updated_at'];
  $result = $this->model->select($fields)->withTrashed()->findOrFail($id);
  $result->append(['options']);

  $columns = ['id', 'food_name', 'food_category', 'price', 'stock', 'calories',
      'food_status', 'description', 'deleted_at', 'created_at', 'updated_at'];
  ```

  `$fields` 控制实际 SQL select，`$columns` 控制详情页元数据；两边都要有 `stock`。

> 💡 **改完即自检**：上面 7 处手补里，`$fillable` 漏补的后果最隐蔽（接口照样 2xx，
> 见 9.3.2）。不必等到 9.6 写测试，tinker 一条命令当场验证（`Model::create()` 绕过
> FormRequest，专测批量赋值这一环）：
>
> ```bash
> php artisan tinker --execute="\$f = App\Models\Food\Food::create(['food_name' => 'fillable 自检', 'food_category' => 1, 'price' => 1, 'stock' => 7, 'food_status' => 1])->refresh(); echo \$f->stock . PHP_EOL; \$f->forceDelete();"
> # → 7（stock 真落库）；若输出 0，就是 $fillable 漏补、stock 被静默丢弃
> # 末尾 forceDelete() 即用即清，不留自检数据
> ```

## 9.4 `moo:adder` 加自定义 action：toggleStatus

CRUD 之外的接口（如「上架/下架切换」）用 `moo:adder` 增量追加——**别重跑 `moo:free`**。

### 9.4.1 它是交互式命令，stdin 可以管道喂

`moo:adder --help` 只有两个位置参数 `app`、`folder`，其余全靠交互 prompt，
命令可通过 stdin 依次传入回答：

1. `Choose a controller:`（列出 `<NEW_ONE>` 和现有控制器，输编号）；
2. `Enter: {action} {request} {resource}:`（空格分隔；request / resource 填 `null`
   表示不要——不要 request 就不生成 FormRequest 形参，resource 为空默认 `BaseResource`）；
3. `Enter: {method} {url}:`（如 `post food/{id}/toggle-status`；留空则不加路由）。

> ⚠️ **坑 #24（当前版）**：folder 直接写 `Food`，不要人为补尾斜杠。当前生成器已经
> 自动处理命名空间；写 `Food/` 会出现 `Food//FoodController` 候选。更隐蔽的是：action 已存在时
> 再次运行仍可能重复追加路由，命令不是完全幂等，重跑前先检查 `routes/admin.php`。
>
> ```bash
> printf '1\ntoggleStatus null null\npost food/{id}/toggle-status\n' | php artisan moo:adder admin Food/
> # 候选会显示 Food//FoodController（不要照此运行）
> ```

正确写法（直接写 `Food`）：

```bash
printf '1\ntoggleStatus null null\npost food/{id}/toggle-status\n' | php artisan moo:adder admin Food
```

```
💬 选择控制器:  [0] <NEW_ONE>  [1] Food/FoodController
🎯 Running Controller Adder
  ➕ ./app/Admin/Controllers/Food/FoodController.php ... @toggleStatus():
  ➕ ./routes/admin.php ............ Route post food/{id}/toggle-status
```

### 9.4.2 adder 只产空壳 + 路由，业务逻辑自己填

它在控制器**末尾**追加了一个空壳：

```php
/**
 * toggleStatus
 */
public function toggleStatus(): BaseResource
{
    $result = [];
    return BaseResource::make($result);
}
```

路由插进了 `routes/admin.php` 的 JWT 登录 group 内、`// :insert_code_here:do_not_delete`
标记之前（位置正确），但用的是 FQCN：

```php
Route::post('food/{id}/toggle-status', [App\Admin\Controllers\Food\FoodController::class, 'toggleStatus']);
```

手工收尾三件事：

**① 路由美化**：改用文件头已 `use` 的短类名 `[FoodController::class, 'toggleStatus']`，
去掉多余空行。

**② 空壳改成真实现**（注意 stub 不带 `$id` 形参，要自己加）：

```php
/**
 * 上架/下架切换（权限复用 update，见 $transform_methods）
 */
public function toggleStatus(int|string $id): BaseResource
{
    $result = $this->model->findOrFail($id);
    $result->food_status = $result->food_status === FoodStatus::ON_SHELF->value
        ? FoodStatus::OFF_SHELF->value
        : FoodStatus::ON_SHELF->value;
    $result->save();

    return BaseResource::make($result);
}
```

头部加 `use App\Models\Food\Enums\FoodStatus;`。按本生态约定枚举**不进 `$casts`**
（坑 #19 的教训），字段是裸 int，比较时用 `->value`。

**③ 权限接线**：类属性里加

```php
protected array $transform_methods = [
    'toggleStatus' => 'update',
];
```

**为什么用 transform 复用 update 权限，而不是 `@acl` 注册新权限？**
「切换上下架」本质上就是一种更新——能改 food 的人就该能切它的状态，
没必要在授权页多出一个独立勾选项。这套生态本身就有先例：scaffold 的控制器基类
（`moo-scaffold/src/Foundation/Controller.php` 的 `getTransformMethods()`）默认内置
`create => store`、`edit => update`、`restore => trashed` 三组映射——「恢复」复用
「回收站」的权限，而且这些被映射的方法 docblock 都**不带 `@acl`**。道理很直白：
挂了 transform 的 action，`checkAuthorization()` 永远按映射目标（这里是 update）鉴权，
此时再写 `@acl` 只会让授权页多出一个**勾了也不生效的死条目**，两套标注并存反而自相矛盾。
所以规则就一条：**transform 复用权限的 action 不写 `@acl`，复用关系写在 docblock
注释里说明即可**（本节空壳改实现时的注释就是这么写的）。

## 9.5 ACL 与接口文档同步

路由和权限映射变了，把两份派生物刷新（都是再生成区，放心重跑）：


验证 `scaffold/acl/admin.yaml`：toggleStatus 被正确识别为权限复用——

```yaml

  plain_key: admin-food-food-update
  action: toggleStatus
  acl_targets: ['App\Admin\Controllers\Food\FoodController::update']
  route_plain_key: admin-food-food-toggle-status
  acl_transformed: true
```

`acl_transformed: true` + 与 update 相同的 key，说明 9.4 的 `$transform_methods`
被 ACL 工具链完整识别。注意 `config/actions.php`、`lang/*/actions.php`、
`scaffold/acl/admin.yaml` 都是 moo:auth **整文件重写**的——里面手写的注释会被抹掉。

## 9.9 给实体配专属 Resource：链式字段控制

到目前为止 Food 全程裸用 `BaseResource`——它的 `toArray()` 把模型属性原样倒出来。
而生态宣传的 `->show()/->hide()/whenDate()/whenTrashed()` 链式字段控制，要发挥威力
得有一个**每实体的专属 Resource** 当展示面。本节给 admin 分片配一个 `FoodResource`，
只动 show 与 trashed 两个 action（index 保持裸 `BaseResource` 不动，控制示例面）。

### 9.9.1 在 yaml 声明 Resource

`moo:resource` 只为 yaml 中 `controller.resource` 声明的分片生成文件。先在
`tables → foods → controller` 中加入 `resource`：

```yaml
tables:
    foods:
        controller:
            app: ['admin', 'api']
            resource: ['admin']      # ← moo:resource 的输出开关，按分片声明（作者生产项目同款写法）
            class: FoodController
```

本节只开 `admin`（api 分片在 9.8.2 已定为裸 `BaseResource`，不回头扩面）。
yaml 是真相源，改完照例 `moo:fresh`，再生成就有产物了：

```bash
php artisan moo:fresh
php artisan moo:resource Food
#  ✨ ./app/Admin/Resources/Food/FoodResource.php ..................... Created
```

输出目录来自 `config/scaffold.php` 的 `controller.admin.resource_path`
（`app/Admin/Resources/`），HTTP 分片自此「四件套」补齐成 Controllers / Requests /
Resources 三兄弟目录。Resource 和 Model/Controller 一样是「生成一次」区
（已存在则跳过，`-f` 才覆盖）——业务字段映射写在这里是安全的。

### 9.9.2 生成的 FoodResource 与四个条件方法

生成的类直接可用，骨架只做了两处教学微调（`whenDate` 写明格式、`whenTrashed`
里把 Carbon 格式化），完整版在
`engine/app/Admin/Resources/Food/FoodResource.php`：

```php
class FoodResource extends BaseResource
{
    public function toArray(Request $request): array
    {
        $data = collect([
            'id' => $this->id,
            'food_name' => $this->food_name,
            'food_category' => $this->whenHas('food_category'),
            'food_category_txt' => $this->whenAppended('food_category_txt'),
            // ... price / stock / calories / food_status(_txt) / description 同理
            'deleted_at' => $this->whenTrashed($this->deleted_at?->format('Y-m-d H:i')),
            'created_at' => $this->whenDate('created_at', 'Y-m-d H:i'),
            'updated_at' => $this->whenHas('updated_at'),
            'options' => $this->whenAppended('options'),
        ]);

        // 最后过 filterFields()，调用方仍可链 ->show('id,food_name') / ->hide('price') 二次裁剪
        return $this->filterFields($data);
    }
}
```

四个条件方法（缺席的键不会出现在 JSON 里，靠 `MissingValue` 实现）：

| 方法 | 来源 | 触发条件 | 生成器的默认选型 |
|---|---|---|---|
| `whenHas('x')` | Laravel JsonResource | 查询 select 了该列 | 非索引字段全用它（窄 select 列表不出 null 噪音） |
| `whenAppended('x')` | Laravel JsonResource | `->append(['x'])` 过 | 枚举 `_txt` 文案、`options` 动作列表 |
| `whenDate('x', fmt)` | BaseResource | 列存在 | 日期列统一格式化，默认 `'Y-m-d H:i'` |
| `whenTrashed($v)` | BaseResource | 链过 `->trashed()` | `deleted_at` 只在回收站语境出现 |

收尾的 `filterFields()` 别删——`->show()/->hide()` 这对链式裁剪就靠它落地。
适用场景一句话：**`show()` 给轻量端点白名单瘦身，`hide()` 临时抹掉个别敏感列，
都不必为此写第二个 Resource 类。**

### 9.9.3 接入 Controller：show 与 trashed

`FoodController` 两处替换（import 补 `use App\Admin\Resources\Food\FoodResource;`）：

```php
// trashed()：集合上链 ->trashed()，传播给每个 item 的 whenTrashed
return FoodResource::collection($result)
    ->trashed()
    ->additional([...]);

// show()：详情查的是 withTrashed，已软删的记录链 ->trashed(true) 让 deleted_at 一并输出
return FoodResource::make($result)
    ->trashed($result->trashed())          // SoftDeletes 的 trashed() 返回 bool
    ->additional(['columns' => ColumnsCollection::make($columns)]);
```

集合链能成立是因为 `BaseResourceCollection` 和 `BaseResource` 共用
`BaseResourceTrait`，`processCollection()` 会把集合上的 `trashed/hide/show`
状态逐个传给底下的 Resource。

## 9.10 按需：可回滚的数据迁移

前面几节改的都是**结构增量**（加字段、加接口），生成器和 `migrate` 已经覆盖。Laravel migration
也可以执行少量、快速且必须随结构同步的数据更新；但大数据回填、拆表搬迁或脏数据清洗通常
耗时更长，需要 dry-run、断点恢复和独立回滚，因此更适合一次性 Artisan command。

自己写一次性迁移脚本（`artisan command` 或 `tinker` 脚本）时，下面这套范式能把「跑错了怎么办」
的风险降到最低。**这是通用方法论，不绑定任何具体迁移**：

1. **dry-run 默认**：脚本默认只统计「会改多少行、改成什么样」，打印样例 diff，**不写库**。
   真正执行必须显式 `--execute`。默认只读，手滑跑一次也不会动数据。
2. **`--execute` 前倒计时**：确认要写库时，打印「即将修改 N 行，5 秒后开始，Ctrl-C 取消」再倒数，
   给最后反悔的机会（生产上跑尤其值）。
3. **manifest 落盘、含 RESTORE SQL**：执行时把「改了哪些行、旧值是什么」写进一个带时间戳的
   manifest 文件，并**直接生成可回滚的 `UPDATE ... WHERE id IN (...)` RESTORE SQL**。出事时
   `mysql < manifest-restore.sql` 就能按行还原，不用翻整库备份。
4. **幂等可重跑**：脚本要能重复跑——已经改好的行第二次跑时识别出来跳过（`WHERE 还没改` 的条件筛选），
   中途失败重跑不会二次污染。
5. **按 manifest 还原**：回滚不是「凭记忆手写 UPDATE」，而是执行第 3 步落盘的 RESTORE SQL。

```text
dry-run（默认，只读统计 + 样例 diff）
  → --execute（倒计时 5s）
    → 写库 + 落 manifest（含每行旧值 + RESTORE SQL）
      → 幂等：重跑跳过已改行
        → 出事：mysql < manifest-restore.sql 按行还原
```

> 这套范式和 `backup.sh` 的全库备份是**两层**：全库备份是最后兜底（粒度粗、还原是整库回退），
> manifest RESTORE 是精准回滚（只还原这次动过的行）。破坏性迁移上线前，`DEPLOY-CHECKLIST.md` 的
> Rollback 决策表会明确「代码可 `pull.sh --tag` 秒回退，数据按迁移的 RESTORE 预案单独还原」。

### 迁移前先对账：`db-yaml-drift-probe.php` 只读漂移探针

写数据迁移前，最好先确认「库表实际结构」和「scaffold yaml 声明」没有静默漂移——否则你以为在改
A 列、实际库里 A 列类型/是否 nullable 早跟 yaml 对不上，迁移逻辑就建在流沙上。仓库根带了只读探针：

```bash
php tools/db-yaml-drift-probe.php        # 从仓库根跑，读 engine/.env 拿 DB 凭据
```

它逐列比对 `engine/scaffold/database/*.yaml` 与实际 MySQL `information_schema`，输出三级漂移报告到
`tools/db-yaml-drift.md`（该文件已 gitignore，含 host 库表结构、不入仓）：

- **high**：列在 DB 缺失 / 类型族不符 / 未识别的 yaml 简写 —— 必修
- **mid**：nullable 不一致 / DB 有列但 yaml 未声明（可能是待下线的 legacy 列） —— 需评估
- **low**：varchar/char 宽度差 —— 低优

**只读、无 `--apply`**：它只读库 + 写一个 md，绝不改任何 schema，可以放心在生产跑一次看现状。
它还会跟 `engine/database/migrations` 交叉对账，把「已立 drop migration、待 `migrate` 执行」的表标出来，
区分「历史遗留」和「计划内下线」。

## 9.11 按需：升级前后对拍

`app/Console/Commands/` 下随骨架带了三个 artisan 命令，是「升级 / 迁移前后」把风险摁住的标准件。
平时用不上，但一旦要动 scaffold 大版本、接入 / 升级 moo-system、或导入一份历史生产库，它们能把
「哪儿悄悄坏了」变成一份可 diff 的证据，而不是等线上报错才发现。三者口径统一：**只读 / dry-run 优先**。

| 命令 | 干什么 | 典型时机 |
|---|---|---|
| `php artisan app:dump-acl-keys` | 导出全部 @acl 动作的明文 key + 16 位 md5 片段 + 白名单 + 角色现值，落 JSON | **升级 scaffold 前后**各跑一次，对拍 md5 有没有漂移（漂了 = 授权没动却全员 403） |
| `php artisan smoke:get-admin` | 用真实 admin 遍历全部 `api/admin` GET 路由，记录状态 + 响应体摘要，落 JSON 基线 | **升级前存基线、升级后再跑对拍**；默认生成唯一文件且隔离 public 导出产物，服务器 5xx（业务 522 除外）/ 抛异常时非零退出 |
| `php artisan app:reconcile-migrations-ledger` | 把导入库里漂了名的老迁移文件名对齐成仓库新文件名（batch 保留），消灭「假 Pending」 | **导入历史生产库后、跑 migrate 前**的前置加固；`--execute` 才写库，且落可还原 manifest |

一条命令示例（升级前存三份基线）：

```bash
php artisan app:dump-acl-keys                 # → storage/app/acl/acl-keys-scaffold-<ver>.json
php artisan smoke:get-admin                   # → storage/app/smoke/smoke-get-admin-<时间戳>-<随机后缀>.json
php artisan app:reconcile-migrations-ledger   # dry-run：只出对照表，账本干净时报「待改写 0」
```

> 三份产物都落在 `storage/app/**`（已 gitignore，不入仓）。升级 / 迁移做完再各跑一次，`diff` 两份
> JSON 就能定位回归——这正是 9.10 「先对账、留可还原证据」思路在升级场景的延伸。
> `smoke:get-admin` 只有显式传 `--out=app/smoke/approved-baseline.json` 时才会覆盖指定文件；
> 默认路径每次唯一，避免一次裸跑毁掉上次证据。命令会把 public 磁盘替换成临时 fake，授权导出等
> GET 动作不会在 `storage/app/public` 留下 XLSX；任一服务器 5xx（业务契约 522 除外）或捕获异常
> 都会保留快照并返回状态 1。

## 9.12 按需：旧前端响应适配

scaffold 2.99 的若干接口响应形状是**面向新代前端**（antdv-next 的语义）定的。老代前端（Element Plus）
消费同一批接口时，不该让后端回退形状，而是**在前端侧做一次归一化**——后端保持 2.99 契约，前端拍平 / 改名。
下面四条对照均为宿主项目实战验证过的差异：

| 主题 | 2.99 响应形状（新代前端直吃） | 老代（Element Plus）前端侧归一化 |
|---|---|---|
| 表单控件 `form_widgets` | **二维行结构**（按行分组的数组，一行可放多个控件） | 拍平成一维控件列表再渲染 |
| 表格列固定 | `fixed: 'end'`（语义化方位） | `'end'` → `'right'`（Element 用物理方位） |
| 部门树 | **数组包根**（顶层是数组，根节点在数组里） | 取首个元素 `tree[0]` 作为单根 |
| 授权接口 | 顶层 `data` + 同级 `personnels` 字段 | 按 `data` / `personnels` 两段分别取用 |

> 一句话原则：**响应形状锚定新代前端，代际差异由前端归一化吸收**。后端不为迁就旧前端而分叉形状，
> 否则新老两套响应长期并存，最后谁都不敢改。
